# Storefront browser tests and visual review

Playwright 1.64.0 (exact pin). Chromium only. Every state is captured at **1440, 390 and 375** px.

| Command (in `web/`) | What it does |
|---|---|
| `npm run e2e` | Builds both bundles and the test-only component gallery, serves them with `vite preview` on 4380 (store), 4381 (operator) and 4382 (gallery), and runs the mocked-mode tests. Screenshots go to `e2e-output/screens/<width>/<state>.png`. |
| `npm run e2e:review` | Writes `e2e-output/review/index.html`: each capture beside its approved artboard, per width. Artboards are read from `docs/design/artboards/` (local only; `ARTBOARDS_DIR` overrides). |
| `E2E_STACK_URL=http://127.0.0.1:18000 npx playwright test` | Stack mode: runs only `*.stack.spec.ts` against a running preview project, without mocks. Never point it at the live stack. |
| `npm run dev:store` / `npm run dev:operator` | Hot-reload dev servers on 127.0.0.1:5180 / 5181, proxying API calls to the preview project (`OBSERVA_GATEWAY_URL`, default `http://127.0.0.1:18000`; `OBSERVA_CONTROLLER_URL`, default `:18090`). Live ports 8000/8090 are refused. |

All output (`e2e-output/`) is git-ignored and kept out of the Docker build context.

## Harness rules (`support/harness.ts`)
- **Strict mocks:** only the built bundle (`/ui/next/…`, served from `dist/` on disk by the real server's rules: assets and licences as files, any other path the entry page, unknown files 404), `/favicon.ico` (404) and `/ui/config` (from fixtures) are answered without a mock. The `vite preview` servers only give each origin an address: going through them stalled for about 10 s now and then under parallel load. Every other request needs a typed handler for its own origin: `api.onGateway(method, "<Gateway OpenAPI path>", …)` answers only on the storefront origin, and `api.onController(…)` only on the operator origin. These are aborted and recorded:
  - an unmocked same-origin request;
  - any request to another origin, such as the live gateway on :8000;
  - any WebSocket.
  
  Routing covers the whole browser context, popups included. A test fails at teardown if a violation is left, unless it takes them with `api.takeViolations()`. A test with `test.fail` proves that rule.
- **No proxy behind the mocks:** `vite preview` runs with an empty proxy, so a request that slipped through could not reach any stack. Stack mode refuses a live `E2E_STACK_URL`.
- **Fixtures come from the system, not the artboards (audit item 5):** `fixtures/gateway.ts` is the seeded catalogue (checked against `scripts/init-db.sql`), typed by the generated API types.
- **Component gallery (test-only):** `gallery/` is built by `vite.gallery.config.ts` into `e2e-output/gallery-dist` and never ships (the Docker image copies only `dist/`). It shows each shared component in every state (`GALLERY_URL`) and the full and focused store headers (`?view=headers`), including items that later slices enable. Its origin serves only its own files and `/ui/config`; it has no API.
- **Captures:** `capture(stateId)` accepts only ids from `coverage.ts` or `HARNESS_STATES` (the two shells, `gallery-components`, `gallery-headers`), waits for fonts, disables animations and takes a full-page screenshot.
- **Diagnostics:** a failing test, or one with leftover violations, gets a `browser-diagnostics` attachment: console errors, failed requests, violations and the per-request routing log. Non-JSON request bodies reach handlers as text. An exception in a handler is recorded as a violation instead of crashing the run.
- **Two workers:** more parallel browsers starved the preview servers on a workstation and caused timeouts. 54 of 54 passed across 3 repeats with 2 workers.

## Checkout safety tests to implement (P4-D to P4-F)
These follow the approved outcome rules:
- A POST result is definite only when the response carries a `CheckoutResult` for this `attempt_ref`. Failures carry it inside the error envelope's `details` (`services/shared/web.py` `error_response`).
- **The unconfirmed-attempt record (reference, lines, time) is written before the POST is sent**, so nothing a browser does afterwards can lose an attempt that may have been placed.

**Reading responses**
- E1: 201 and 202 are read from the body. 402, 409 `insufficient_stock` and 503 or 500 are read from `details`.
- E2: Any error without `details` is unknown. That includes Gateway 502/504 dependency errors, 422 validation errors, and 409 `idempotency_conflict` or `attempt_abandoned` on POST.
- E3: A `CheckoutResult` whose `attempt_ref` differs from the attempt sent is unknown, not definite.

**Refresh and navigation**
- R1: Reload while the POST is in flight → after reload, "Status unknown" with the same `ATT-` reference. No POST is sent again.
- R2: Reload on the unknown screen → the same state. Check status reuses the reference.
- R3: Reload while processing (202) → resumes polling with `GET /api/attempts/{ref}`, never a POST.
- R4: Reload on success → the order number is re-read from the server. The cart stays cleared.
- R5: Back or forward to /checkout after success → no resubmission. An empty cart cannot be submitted.

**Multiple tabs**
- T1: Two tabs allocate references at the same moment → distinct references (the allocator is serialised across tabs).
- T2: Cart edits in one tab appear in the other (storage events).
- T3: Success in tab A empties the cart in tab B. B's checkout re-quotes and cannot submit the stale cart.
- T4: An unconfirmed attempt made in tab A appears in tab B's My Orders. Resolving it in B updates A.
- T5: Both tabs press Check status on the same reference → both read; resolve is idempotent and both end in the same state.
- T5b: A stale tab POSTs a reference already resolved as abandoned in the other tab → 409 `attempt_abandoned` without details. It follows U6, and Check status then shows not placed.
- T6: The same cart submitted while an unconfirmed attempt with the same lines exists → the user is asked to check that attempt first. A new attempt gets a new reference.

**Unresolved attempts**
- U1: Network error on POST → unknown. The record is kept until a definite outcome.
- U2: Response lost after the server committed (the mock records the order, then returns a network error) → Check status shows confirmed. No duplicate order.
- U3: Check status → GET 404 → resolve → abandoned → "not placed, safe to retry". The retry uses a new reference.
- U3b: Resolve may instead return confirmed (201), processing (202) or declined (402). That happens when the attempt was recorded between the GET and the resolve, or when resolve settles a stalled attempt. Each is shown as that outcome.
- U4: GET returns processing → polls with 1, 2, 4 and 8 s backoff for about 60 s, then "still processing, check again".
- U5: Check status itself fails (network) → stays unknown. Resolve is never called after a failed GET.
- U6: 409 `idempotency_conflict` or `attempt_abandoned` on POST (no `details`) → this POST placed nothing, but the reference stays unconfirmed. Go to Check status and keep the record, because the reference may hold another, possibly confirmed, checkout.
- U7: Every click sends exactly one POST, never retried automatically. A double-click sends one POST.
- U8: An unconfirmed record older than the 50-order server window is still checkable from My Orders.
- U9 (documented limitation): clearing site data loses unconfirmed records and the anonymous customer ID. The server still holds the attempt.

### Status after P4-E (`checkout.spec.ts`, `recovery.spec.ts`, `test/checkout-*.test.ts`)
- Covered: E1-E3, R1-R5, T2 (`cart.spec.ts`), T3, T5, T5b, T6 (paused while unconfirmed), U1-U7, 422 on checkout (heals through resolve) and on Check status (stays unknown), and a privacy scan after recovery (storage, IndexedDB, address, status requests).
- How duplicates are prevented: `src/store/checkout/gate.ts` decides in one IndexedDB read-write transaction (refuse while any attempt is stored, advance the reference counter, store the attempt). IndexedDB runs such transactions one at a time across tabs; localStorage only mirrors the gate for the screens and is re-read from it after every change, so a stale tab cannot bring a settled attempt back.
- **Fail closed:** without IndexedDB (or when it refuses to open) nothing is sent; the page says the reference could not be saved. There is no Web Locks or localStorage fallback any more.
- **Race tests can fail:** both tabs press at one shared instant (`pressTogether`). A mutant test patches the page's IndexedDB in the browser (never the shipped code) so the gate's check reads nothing, and asserts it then sees exactly two POSTs. `test/checkout-gate.test.ts` does the same at the unit seam with two connections to one fake-indexeddb database, plus a gate that reads and writes in separate transactions (a race-only bug the same check catches).
- **Check status:** GET first. Only 404 `attempt_not_found`, or a still-processing answer after polling gave up (Check again), leads to one resolve. Requests carry the reference and the customer ID stored with the attempt; never contact data.
- **Polling:** GET only, 1, 2, 4, 8, 8 ... s, about 60 s, then "still processing" with Check again. A failed poll keeps the attempt processing; leaving the screen stops polling. Tests step through it with `page.clock`.
- **Confirmed cart effect, exactly once (D4):** `gateConfirm` removes the attempt and journals its effect in one transaction; `cart.applyConfirmed` takes the units out and records the reference in the same `observa.cart` value (one write), starting from what storage holds. The journal (20 newest, replayed on start for 24 hours) covers a crash between the two.
- **R4:** after a confirmed order the address becomes `/checkout?attempt=ATT-…` (the reference only). A reload re-reads it with GET, read-only; anything but a matching confirmed order shows the page as usual.

### Status after P4-F (`orders.spec.ts`, `test/orders-*.test.ts*`)
- Covered: T4 (an unconfirmed attempt shows in every tab's My Orders; resolving it in one updates both) and U8 (an unconfirmed attempt older than the 50 orders the server returns is still listed from this browser and checkable). Every My Orders artboard state at 1440/390/375.
- **Merge** (`src/store/orders/merge.ts`): one row per attempt reference; the server's answer wins; an attempt the server does not list is shown from the gate as Status unknown or Processing.
- **Reconciliation** (`flow.reconcile`): when the list has a definite result for an attempt this browser still holds, it is settled through the same gate path as Check status (no request, never resolve). Only for a valid result for the same reference, listed for the customer ID the attempt was sent with. A confirmed order's cart effect still happens once: tests reconcile twice, reconcile and check in two tabs, and reload twice.
- **Check status** on My Orders and order details is the P4-E `flow.check` (GET first; resolve only after 404 `attempt_not_found`). A processing order the server lists but this browser does not hold is refreshed by rereading the list, never by resolve. An attempt reference neither listed nor held is looked up read-only (GET) on its detail page.
- **Safety review fixes:** Check status from My Orders is quiet (it settles the attempt but never puts an outcome on the checkout page); "unknown" never overwrites "processing" (decided inside the gate transaction); a failed refresh keeps the loaded list and every held attempt on screen with Try again; the detail page stops waiting when a reread fails.
- **Known limitations (safe direction):** an attempt another tab is still sending shows as Status unknown and can be checked, which may fence it (that tab then gets 409 and shows not placed); a stale tab's cart write can undo an applied subtraction and its marker together (repaired by the journal replay on the next start within 24 hours, never subtracted twice); a new random reference prefix after IndexedDB alone is cleared could, at 1 in 65,536, collide with an old reference of the same customer.
- **Crash journal retention, reviewed:** an effect is journalled when the gate confirms it (`confirmed_at` = that moment), so a very old unknown attempt confirmed today is replayable for 24 hours from today. Gaps (documented, safe direction): a crash followed by more than 24 hours before the next page start leaves the ordered units in the cart; clearing only localStorage within 24 hours re-applies journalled effects to the new cart.

### P5-F: local contract harness (Gate A passed; T1 verified)

- **Harness exit codes:** 0 clean, 2 refused, 3 start failure, 4 forced, 5 shutdown failed. After server tasks finish, a recorded server exception or a lifespan `shutdown_failed` flag prints `contract-harness shutdown failed: <reason>` to stderr and prevents the clean marker. An already-set start-failure code takes precedence, followed by forced shutdown, then shutdown failure.
- **Controller-to-target transport (found by a T1 run):** one valid `POST /faults/activate` got `503 target_unavailable` about 50 ms later while the stub recorded no call. A reproduced connection-reuse race is the *likely*, not proven, cause: the controller discarded the underlying exception, so the original failure cannot be attributed with certainty. In isolation (the real stub under uvicorn, the previous pooled client) 2 of 103 trials inside the race window failed with `httpx.RemoteProtocolError: Server disconnected without sending a response` and no stub record, each just before the server's idle deadline (1 of 28 at 4.95 s idle against uvicorn's default 5 s keep-alive; 1 of 75 at 0.995 s idle with the stub's keep-alive set to 1 s). Connections already closed were replaced correctly, and with no idle reuse 0 of 87 trials in the same windows failed. The per-file counts and settings were kept in uncommitted local evidence rather than in the repository, because the saved trial records do not themselves carry the keep-alive setting. The controller's client now never reuses an idle connection (`target_client()` in `controllers/fault_injector/app.py`; timeout 3 s and 4 connections unchanged; commands are still never retried, and the confirmed-only, unknown-state and error semantics are unchanged). Deterministic regression tests: `tests/unit/test_controller_target_transport.py`. Not changed, recorded as follow-ups: the controller's health-probe client (`health.py`) and the storefront services' shared client (`services/shared/client.py`, whose `DependencyClient` does not map this error) can meet the same race.
- **Scope and modes:** contract mode runs the real controller (guard included) on `127.0.0.1:18190`, with stub targets, stub health and test control on `127.0.0.1:18191` in one Python process. It has no Docker dependency and does not send faults to business services. Mocked, stack and contract modes select separate specs and cannot be combined. `npm run e2e:contract` builds and supplies explicit harness origins; importing the Playwright config supplies no defaults and changes no environment variables.
- **Configuration and server isolation:** TypeScript and Python checks refuse missing or malformed settings, live/preview ports from `contracts/stack-ports.json`, shared ports, noncanonical controller/control origins, nonempty inherited proxies and settings that could select real services. Python binds only `127.0.0.1`; controller URLs and public links name harness ports; the controller's client for its stub targets is the controller's own `target_client()` (see the "Controller-to-target transport" bullet) with proxies ignored, and its documentation routes are removed. Readiness waits for the exact harness stdout line, with no URL or port probe. Startup, shutdown, lifetime and the whole Playwright run have bounds. Only regular `incidents.jsonl` and `incidents.tmp` files under the fixed, git-ignored journal folder are cleared at startup; symlinks and directories at either filename are refused. The default resolved output root must equal the repository's journal anchor. The journal directory itself must be neither a symlink nor a junction, and must resolve to exactly its anchored relative location, including when a link would stay inside the output root. These are pre-deletion checks: the TOCTOU window between checking and deleting, under concurrent local filesystem mutation, is not closed.
- **Cooperative shutdown:** contract mode's global teardown runs before Playwright's web-server plugin teardown, as confirmed by reading the installed runner. First it asks the harness which process it is (`GET /__test__/alive` on the control origin, header-protected; the answer must be a plausible process id that is neither the runner nor its parent), then POSTs `/__test__/shutdown`, never following redirects and with per-request time limits, and finally waits, boundedly, until THAT PROCESS is gone (signal 0 only asks whether it exists). It contacts only the harness control origin. It logs `contract-harness cooperative shutdown: <outcome>` (`exited`, `timeout`, `unreachable` or `refused`, with detail when available). A closed port is deliberately not used as evidence: uvicorn closes its listeners before the controller's shutdown has finished, so a refused connection would show up too early. The harness itself sets `should_exit` on both servers and waits for them to finish; only an unforced normal stop prints `contract-harness stopped cleanly` to stdout and exits 0. If a server needs forcing or cancellation, it prints `contract-harness stopped by force` to stderr and exits 4; startup failures keep their refusal/failure codes and never claim a clean stop. Lifetime-limit and signal stops use the same cleanup path. Playwright's bounded process-kill fallback remains if the process does not exit in time; on Windows its web-server plugin rejects signal-based graceful shutdown and force-kills the process tree, which bypasses Python cleanup and cannot establish a clean stop. The cooperative path and its diagnostics are unit-tested with fakes, and it has been seen working on Windows: every browser run of the Gate A retest and of T1 logged `exited` together with the harness's `stopped cleanly` line.
- **Reported Gate A failure:** A2 delivered a 302 using `route.fulfill`; Chromium itself followed the later hop to the harness control `/sentinel` and received 200. Playwright routed only the first request of that chain. The earlier claim that fulfilling each hop would cause the next hop to be routed was wrong. The `request`-event audit only detects an off-origin request; detection after contact is not prevention.
- **Reissued-request layer:** allowed requests delivered to the route handler normally use `route.fetch` with redirects disabled and `X-Contract-Reissued: route.fetch`. A fetch failure is recorded and aborted. A redirect answer (300-399 except cache status 304) is refused, recorded and never delivered to Chromium, including a redirect to the controller's own origin. This decision logic is unit-tested, and the browser behaviour was verified by the Gate A retest (A2 10 of 10 on desktop; A3 30 of 30, twice, at 1440, 390 and 375). Controller-side header records show what the controller received, without keeping cookies, authorization or other unlisted headers. A page can forge a reissue label on a genuine pass; the fixture now spends the pass, aborts that request and records the forgery. Reissues always replace any caller label. Node helper contexts also disable redirect following.
- **Chromium boundary layer:** before test navigation, the fixture installs `Network.setBlockedURLs` on its page's CDP session. The full ordered allow-list permits the controller origin first, then blocks all other `http`, `https`, `ws`, `wss` and `ftp` destinations. Only the routed-layer self-test requests an additional allow entry for exactly the harness control `/sentinel` path; every other control path remains blocked. The handle permits that relaxation only once per test and propagates installation errors. Initial installation failure prevents the test body from running. Pattern semantics are unit-tested with Node's global `URLPattern`, not Chromium's matcher; browser behaviour and redirect-hop enforcement were verified by the Gate A retest. No machine-wide firewall or network setting is changed.
- **Node reissue policy (unit-tested):** `support/route-policy.ts` decides each HTTP request delivered to the route handler by parsed-origin equality with the controller's http origin. Equivalent spellings of that same origin and user info are accepted by design. An off-origin request is aborted without consulting genuine passes. For an allowed origin, no pass means a labelled reissue; a matching pass without a caller label means `route.continue`. `route.fetch` receives only the browser's headers with the label replaced, `maxRedirects: 0` and a timeout, with no URL, method or body override. Non-network URLs, internal browser activity, DNS resolution and speculative preconnect/prefetch are outside the prevention claim and have no evidence here. The fixture wiring (route handler, boundary installation order and redirect-refusal call) is covered only by browser self-tests, not socket-free unit tests; a regression in that wiring would be caught only when those tests run.
- **Redirect source: the sentinel only (unit-tested):** the harness-only `/__harness__/redirect` serves exactly one kind of target, the `/sentinel` path (plain segments only, optional query or fragment) on the harness control origin `http://127.0.0.1:<control port>`. Its redirect answer has no body and no content-type, only the status and Location plus standard response headers. Everything else is refused, including every live and preview port, the controller's own origin, unrelated local services, other spellings of the host (`localhost`, IPv6, `127.1`, hexadecimal or decimal IPv4, a trailing dot, user info, upper case, https) and dot segments or encodings in the path. A deny-list of known ports would be incomplete, so the rule is an allow-list; without a control port the recorder serves nothing, and it refuses to be built with a live, preview or out-of-range port. Even with a valid header or nonce the harness therefore cannot send a browser to any real or unrelated service, whatever the browser boundary does.
- **Coverage limits (no claim of full browser isolation is made):** only the fixture page has this CDP boundary. A second page or popup is flagged and closed, but its first request may escape the handler. Dedicated workers and out-of-process iframes are outside that CDP session. A genuine pass uses `route.continue`, lets Chromium follow redirects itself, and relies only on the network boundary for those hops. The fixture also closes and records WebSockets and disables service workers; `ftp`/`ws` pattern enforcement remains untested in a browser. Live and preview ports are covered by the allow-list and verified by pattern unit tests only, never by contacting them.
- **Sentinel contact ledger:** the control app's outermost ASGI wrapper records every HTTP method and WebSocket handshake at `/sentinel` and `/sentinel/…`, before the Host guard and method routing. Classification extracts the path from an absolute-form target regardless of authority or scheme case, then percent-decodes once before the case-sensitive path check. This follows how the server reads such targets; over-counting an already decoded target is accepted because it produces a false failure, not a missed contact. Case variants, double-leading slashes and lookalike paths are not sentinel contacts. The total is uncapped; the bounded contact list preserves the original scope path and keeps only method, path and timestamp, never queries or headers. Reset clears both. A WebSocket contact is recorded and passed through, without being accepted by the harness.
- **Retest evidence:** `contract.isolation.contract.spec.ts` separately checks redirect refusal by the routed layer, a genuine redirect under the browser boundary, a direct forbidden fetch, JSON leak detection and WebSocket recording. Its only forbidden destination is the harness control `/sentinel`. Test (i) opens the controller page and then exempts exactly the sentinel from the CDP boundary, so the boundary cannot mask a route-handler failure: if the route handler delivered the 302, Chromium could reach the exempt sentinel and its ledger would reveal the contact. It requires exactly one redirect diagnostic bound to that request's source URL, status and target, with the nonce redacted. Tests (ii) and (iii) keep the full boundary. Both require result `error`, zero sentinel hits and an empty contact ledger; off-origin audit entries are optional, but every entry must equal the exact requested sentinel URL, never a prefix or lookalike. The genuine-boundary test also requires a recorded, unlabelled redirect-source request and includes any audit entries in its `boundary-evidence` annotation. The WebSocket test checks both ledgers and requires exactly its one `websocket <url>` diagnostic. A recorded off-origin URL alone proves detection, not prevention. Unrelated consumed violations fail every self-test. These browser self-tests passed in the Gate A retest (A2 10 of 10 on desktop; A3 30 of 30, twice, across the three viewports) and have since gained cases for the Node scan of re-issued responses: a held ground-truth probe, cancellation by the page, work still pending at the end of a test, and compressed responses.
- **Redirect self-test authorization:** Node mints a single-use nonce for each redirect test, and the browser uses a simple GET with `mode: "no-cors"` and no custom header, so CORS/preflight cannot stand in for the boundary. The controller recorder never keeps the nonce query, and fixture violation strings redact nonce values. A nonce may remain in Playwright traces of the single request that used it. The tests require an error, zero sentinel hits and no contacts; browser enforcement was verified by the Gate A retest.
- **T1 contract specs and results:** `operator.contract.spec.ts`, `operator-manual.contract.spec.ts`, `operator-cycle.contract.spec.ts` and `operator-resilience.contract.spec.ts` drive the real controller against the stubs at 1440, 390 and 375 (48 tests per project, 144 listed, 141 passed and 3 skipped per run: the three phone-only tests do not run at 1440). The full matrix passed twice on the final test code with a clean harness shutdown, no connection to a live or preview port observed, and Docker unchanged. Run it with `npm run e2e:contract` (it builds first, takes about 8 minutes, and needs explicit human approval).
- **Known limits of the verification:** the socket sampler used for the local evidence matches only exact loopback addresses, omits TCPv6 and samples periodically, so its "0" means "no matching connection observed"; it corroborates the routing and CDP enforcement and does not replace them. The mocked suite (`npm run e2e`) is accepted with a known-flake exception: the gallery tests in `brand-chrome.spec.ts` and `recovery.spec.ts:131` failed intermittently (see the handoff), unresolved and carried into P6. T2 (one real fault and one short cycle on the throwaway preview) is deferred to P5-G Stage 2 and is not covered by these results.
- **Other checks and stack mode:** decoded JSON keys and strings are scanned for ground truth on ordinary JSON responses, including error responses; HTML/JS/CSS/fonts are not scanned. The leak scan never reads any 3xx body, even if its content-type says JSON; a read or parse failure on an inspectable JSON answer remains a violation. The harness control API requires its custom header. Unit tests exercise the stub, recorder, redirect source, configuration and lifecycle with uvicorn faked and no sockets. Stack tests with `E2E_STACK_BUNDLE=local` serve the local operator entry point, hashed assets and licence texts only when the controller origin is allowed; API requests still reach the preview controller. Storefront-only stack behaviour is unchanged. No preview service was contacted for these checks.
